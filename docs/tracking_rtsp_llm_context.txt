LLM / maintainer context: tracking pages, RTSP URL flow, and session behavior
================================================================================
Last updated: 2026-03 (conversation-derived summary; verify against code if unsure)

Purpose
-------
This document summarizes design decisions, file locations, API behavior, bugs
that were hit during implementation, and what was reverted—so future sessions
can reason about the tracking UI without re-deriving from git history alone.


High-level product split
------------------------
1) /tracking
   - YAML-driven default capture source (defaults.yaml "source" + tuning).
   - UI: PiCamera-style camera + sensor mode (when /api/cameras exists), model,
     FPS, confidence, classes, Start/Stop.
   - No per-page RTSP URL field, no "input source type" selector, no
     "Apply input settings" for switching Pi vs OpenCV vs URL on one page.

2) /tracking-rtsp
   - User supplies an explicit stream URL (RTSP or anything OpenCV can open).
   - Source for that session is NOT taken from defaults.yaml; it is set only
     via POST JSON with { "url": "..." } (and optional tuning keys).
   - Same WebRTC + /ws-tracking pipeline as /tracking once the track exists.

Rationale: keep the default tracking page simple; isolate "paste a network
URL" behind a dedicated route and API so YAML stays the default for the main
viewer.


Backend: stream_fastapi/session.py
----------------------------------
- _default_tracking_options_dict()
  - Full baseline from resolve_source_spec(defaults.yaml source) + tuning
    (fps, model, conf, tracker, classes).

- _tuning_only_defaults_from_yaml()
  - Only tuning fields from YAML—no capture source. Used when building an
    RTSP-first track without reading defaults.yaml for *source*.

- _replace_tracking_track_from_merged(session_id, merged)
  - Shared path: resolve class IDs, source_spec_from_flat(merged), stop old
    TrackingVideoTrack, construct new TrackingVideoTrack.

- apply_tracking_patch(session_id, body)
  - Merges PATCH keys into current options (or yaml baseline), then replaces
    the track via _replace_tracking_track_from_merged.

- apply_tracking_rtsp_url(session_id, url, body=None)
  - Forces OpenCV-style source: source_type OpenCV, url, camera_index 0,
    sensor_mode_index null. Base options = existing track.get_options() if
    any, else _tuning_only_defaults_from_yaml(). Optional body merges
    model_key, target_fps, conf, classes, etc.

- get_tracking_rtsp_options_dict(session_id)
  - If a tracking track exists: returns get_options() plus "url" when
    capture_ref is a string.
  - If no track: tuning defaults + source placeholders (no yaml capture).
  - Does NOT call get_tracking_track() (avoids auto-creating a yaml-default
    capture just by opening the RTSP options page).

- get_tracking_track(session_id)
  - Still creates a yaml-default TrackingVideoTrack if missing (used by
    /tracking/options, /tracking/load-model, etc.).


Backend: stream_fastapi/routes/tracking_viewer.py
-------------------------------------------------
Routes (non-exhaustive; see file for full list):
- GET  /tracking              -> tracking.html
- GET  /tracking-rtsp         -> tracking_rtsp.html
- GET  /tracking/load-model   -> loads YOLO on session track (asyncio.to_thread)
- GET  /tracking/options      -> get_tracking_track + models/classes lists
- PATCH /tracking/options     -> apply_tracking_patch
- GET  /tracking/rtsp/options -> get_tracking_rtsp_options_dict (no yaml capture)
- POST /tracking/rtsp         -> apply_tracking_rtsp_url(JSON), returns options

Logging (INFO) was added around RTSP options, POST /tracking/rtsp, and
load-model for debugging slow or stuck requests (e.g. yolo load_config).


Frontend: files and responsibilities
------------------------------------
- frontend/tracking.html
  - Simpler layout: camera/mode + tuning + Start/Stop.
  - streamPage({ wsPath: "/ws-tracking", loadModel, optionsUrl: "/tracking/options" })

- frontend/js/stream.js
  - streamPage(config): WebRTC, GET/PATCH /tracking/options, Pi camera lists,
    load-model before Start on the main tracking page.
  - window.streamPage = streamPage (explicit global for older/debug contexts).

- frontend/tracking_rtsp.html
  - URL field, Connect, tuning controls, Start/Stop.
  - Does NOT load stream.js for the RTSP UI (avoids one large dependency for
    that page).
  - Injects frontend/js/tracking_rtsp.js using:
      new URL("../static/js/tracking_rtsp.js", window.location.href).href
    so static assets resolve correctly when the app is mounted under a path
    prefix (relative to /tracking-rtsp).

- frontend/js/tracking_rtsp.js
  - trackingRtspPage(config): POST /tracking/rtsp, GET /tracking/rtsp/options,
    optional background warmup GET /tracking/load-model, WebRTC same as
    stream.js for tracking.
  - window.trackingRtspPage = trackingRtspPage
  - Bootstrap in tracking_rtsp.html: script onload runs trackingRtspPage(...);
    onerror shows a clear message if the script fails to load.

Session alignment (critical)
----------------------------
- HttpOnly cookie "session_id" may not be readable from JS.
- GET /tracking/options and RTSP endpoints return session_id in JSON; the
  frontend stores it in sessionStorage (yolo_session_id).
- WebSocket URL appends ?session_id=<stored> because some clients omit cookies
  on the WebSocket handshake.
- If POST /tracking/rtsp applies to session A but /ws-tracking connects with
  session B, the stream will use the wrong track (or yaml defaults). Always
  verify session_id matches across POST response, storage, and WS URL.


UX / bugs fixed during development
----------------------------------
1) "Stuck on loading" after Connect
   - Cause: sequential GET /tracking/load-model after POST blocks for a long
     time (YOLO weights). UI waited on that request.
   - Fix: after successful POST, mark source ready immediately; run load-model
     warmup in the background; user can press Start; model also loads inside
     the tracking thread if needed.
   - load-model handler uses asyncio.to_thread(track.load_model) so the event
     loop is not blocked for other requests.

2) Initial page stuck on "Loading..." with no console signal
   - Added browser console logs prefixed [tracking-rtsp] and server INFO logs
     on GET /tracking/rtsp/options.
   - Added optional AbortController timeout for the options fetch with a clear
     on-page message.

3) "trackingRtspPage is not a function" / stream.js did not load
   - Causes: 404 on /static/js/stream.js, parse error, or path prefix breaking
     absolute /static/... URLs.
   - Fix: dedicated tracking_rtsp.js; relative resolution of script URL;
     onerror handler; try/catch in bootstrap.

input_sources/resolver.py
-------------------------
- make_frame_stream uses cv2.VideoCapture(spec.capture_ref) for non-PiCamera
  sources (no CAP_FFMPEG wrapper in tree at time of this doc; a trial adding
  FFmpeg + WSL hints was reverted per maintainer request).

- RTSP connection errors: FFmpeg logs (e.g. tcp://host:port) reflect the URL
  actually passed to VideoCapture. A mismatch between an entered LAN URL and
  "localhost" in logs usually means wrong session track, stale session, wrong
  URL pasted, or server-side redirect/SDP—not necessarily OpenCV backend.


What was explicitly reverted / not kept
---------------------------------------
- CAP_FFMPEG + buffer size + WSL-specific hints in resolver.py (reverted).
- WSL paragraph in tracking_rtsp.html hint (reverted).


User-confirmed outcome
----------------------
- After correcting the RTSP URL (earlier confusion included a wrong link),
  the pipeline behaved as expected; remaining connection issues were attributed
  to user-provided URL accuracy rather than this codebase’s session/OpenCV
  wiring.
