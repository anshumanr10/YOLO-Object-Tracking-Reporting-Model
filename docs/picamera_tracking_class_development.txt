# Picamera Tracking & Class Development — Context for LLM Agents

This document summarizes discussions and implementation decisions around Python conventions, the YOLO/config pipeline, and the refactor to robust per-session pi classes with thin FastAPI routes. Use it to gain project context before making further changes.

---

## 1. Project Overview and Pipeline

- **Repo:** YOLO-Object-Tracking-Reporting-Model. FastAPI backend streams live video from a Raspberry Pi camera over WebRTC; two modes: raw camera stream or camera + YOLO object tracking.
- **Pipeline (top to bottom):**
  - **Frontend (browser):** Loads pages (e.g. `/`, `/tracking`), connects WebSocket (`/ws` or `/ws-tracking`).
  - **stream_fastapi:** Routes serve pages and WebSocket endpoints; on WebSocket connect they call `handle_webrtc_connection(..., track_factory=...)`.
  - **webrtc:** Runs signaling and streams the track returned by the factory.
  - **pi/** classes: `Picamera2Source` (raw) or `TrackingVideoTrack` (camera + YOLO). Each is an aiortc `VideoStreamTrack`; capture/tracking loop runs in a background thread, frames go to a queue, `recv()` returns `VideoFrame`.
  - **yolo/** (tracking path only): `config_loader`, `tracker.tracking_frames`, frame sources, video_output, report. No WebRTC or FastAPI in yolo.
- **Important:** The two pi classes are used only by the backend (stream_fastapi → webrtc → pi). The frontend never imports or touches pi or yolo.

## 2. Python Conventions Discussed

### 2.1 Module documentation (docstrings vs Javadocs)

- Python uses **docstrings** (triple-quoted strings as the first statement inside a definition), not block comments like Javadoc.
- Docstrings are runtime-accessible via `obj.__doc__`. Type checking is not built into the interpreter; it is done by external tools (e.g. mypy, pyright) or by explicit runtime checks.
- **Module docstring:** Placed at the top of the file (first statement). Used for `yolo/source_picamera.py` and other modules where we added docs.

### 2.2 Caller–callee and optional parameters

- **Parameters are optional only if they have a default value.** No “all optional by default” rule.
- **Type checking:** Python does not enforce types at runtime from annotations. Responsibility is either:
  - **Static:** Run a type checker (mypy, pyright). Caller is expected to pass correct types when overriding defaults.
  - **Runtime:** Add explicit checks (e.g. `isinstance`) in the callee if desired.
- **Convention adopted for this project:** Defaults come from config (e.g. `yolo/config/defaults.yaml`). Function parameters that mirror config are optional with those defaults. **When a caller overrides a default, the caller is responsible for passing the correct type;** the callee does not perform runtime type/range validation for those overrides (see below).

---

## 3. YOLO Config and model.py Removal

- **Default configuration:** `yolo/config/defaults.yaml` holds model, source (type, etc.), conf, fps, tracking, classes. `yolo/config_loader.py` loads and validates YAML at import/load time; validation ensures stored defaults have correct types and shape.
- **Caller-responsible convention:** Runtime validation was removed from `yolo/model.py` for `confidence_lvl`, `fps_limit`, and `tracking_enabled`; they now just return `float(confidence)`, `int(fps)`, `bool(tracking)` and document that the caller is responsible for valid values.
- **model.py removed entirely:** It only loaded the YOLO model and exposed trivial helpers. Callers (yolo/tracker.py, pi/tracking_source.py, stream_fastapi routes) now instantiate YOLO themselves: `config.load_config()` then `YOLO(config.models[model_key]["weights"])`. No separate `load_model()` module.

---

## 4. Tracker as Module vs Class

- **Decision: keep `yolo/tracker.py` as a module (functions), not a class.** Reasons:
  - The pipeline is stateless and compositional: stream in → generator → consumer. No long-lived “tracker object” that must persist across runs.
  - `tracking_frames(stream, ...)` and `run_tracking(...)` take options per call; no need to hold state in an object.
  - A class would only wrap the same parameters without clear benefit. If later we need one loaded model reused across streams or richer state, a class could be introduced then.

---

## 5. Routes vs pi Classes — Logic Placement

- **Observation:** Routes in `stream_fastapi/routes/` (e.g. `camera_options.py`, `tracking_viewer.py`) were implementing logic that conceptually belongs in the pi layer:
  - **camera_options:** Listed cameras and sensor modes by opening Picamera2 and reading `sensor_modes`; `Picamera2Source` also uses Picamera2 and sensor modes in its capture loop. So “how to get/interpret sensor modes” was duplicated.
  - **tracking_viewer (warmup):** Loaded the default YOLO model via HTTP; `TrackingVideoTrack._tracking_loop` did the same on start. So “load default model” was duplicated.
- **Direction agreed:** Pi classes should own the logic; routes should be thin and call the appropriate methods on the session’s instance.

---

## 6. Instance Lifecycle: Option A vs B vs C

Three options were compared for when and how to create the pi class instances (tracking and camera):

- **Option A — One global instance:** Single tracking and single camera instance for the whole app. **Rejected:** Cannot support multiple users/devices (e.g. PC on Picamera, laptop on RTSP).
- **Option B — Per-session:** One instance per session (session identified by cookie/session ID). Instance is created or retrieved when the user visits the relevant page; warmup and option setters run on that instance before the user clicks Start. **Chosen** because:
  - Warmup can be an **instance method** (`load_model()` on the track), since the instance exists at page load.
  - Supports multiple sessions (e.g. different devices) and future source exclusivity (one source per active instance).
- **Option C — Per-WebSocket:** Instance created when the WebSocket connects (e.g. when the user clicks Start). **Rejected** for the main flow because with Option C, warmup runs at page load **before** any instance exists, so warmup would have to be defined **outside** the class (e.g. standalone function or class method). We wanted all tracking logic, including load_model, inside the class.

**Source exclusivity:** The goal is that each input source (e.g. Picamera, RTSP) can be used by at most one active stream at a time (n sources → 0..n instances). **Not implemented yet;** the current work focused on robust classes and thin routes only. When added, it will require a source registry and binding an instance to a source when the stream starts.

---

## 7. Naming and Scope Decisions

- **Warmup → load_model:** The operation is referred to as **load_model** everywhere (not warmup). API path is `/tracking/load-model`; legacy `/tracking/warmup` remains as an alias.
- **No source exclusivity in this phase:** Only “clean/robust classes + thin routes + minimal frontend” were implemented. Source exclusivity is deferred.

## 8. Implementation Summary (What Was Done)

### 8.1 Session (Option B)

- **`stream_fastapi/session.py`:**
  - `get_session_id(request, response)` — Reads or creates session ID; sets cookie on response. Session is cookie-based only (no login yet; can be layered later).
  - `get_session_id_from_websocket(websocket)` — Reads session ID from the WebSocket request’s Cookie header.
  - `get_tracking_track(session_id)` — Returns the session’s `TrackingVideoTrack` (created with defaults from yolo config if not already present).
  - `get_camera_track(session_id)` — Returns the session’s `Picamera2Source` (created with default camera index if not already present).
- **Bug fix:** Session module lives in `stream_fastapi`, so config import is `from .config import CAMERA_INDEX` (not `..config`).

### 8.2 pi/tracking_source.py (TrackingVideoTrack)

- **load_model():** Loads the current model (from `model_key` or config default), stores on `self._model`. Used so the first frame is not delayed after the user clicks Start.
- **Setters:** `set_fps`, `set_model_key`, `set_conf`, `set_persist`, `set_tracker`, `set_classes`, `set_source_type`, `set_camera_index`, `set_sensor_mode_index`.
- **get_options():** Returns current options for API/UI; classes are returned as class **names** (via config classifications). Used by GET /tracking/options.
- **_tracking_loop:** Uses `self._model` if set, else loads once; builds `track_kwargs` from instance attributes; calls `yolo.tracker.tracking_frames(..., model=self._model)` so a preloaded model is reused.

### 8.3 pi/picamera2_source.py

- **Module-level:** `list_cameras()` — Returns list of camera info dicts from Picamera2. `list_sensor_modes(camera_index)` — Returns list of sensor mode dicts; opens and closes the camera for discovery only.
- **On the class:** `set_camera_index`, `set_sensor_mode_index`, `get_options()` (returns camera_index, sensor_mode_index).

### 8.4 yolo/tracker.py

- **tracking_frames(..., model=None):** If `model` is provided, it is used instead of loading from `model_key`. Allows the pi tracking track to pass a preloaded model.

### 8.5 Routes (thin)

- **camera_options.py:** `/api/cameras` and `/api/cameras/{id}/modes` call `picamera2_source.list_cameras()` and `list_sensor_modes()`. `GET/PATCH /api/stream/options` get/update the session’s camera track options (delegate to track’s get_options/setters).
- **tracking_viewer.py:** `GET /tracking/load-model` — Gets session’s tracking track, calls `track.load_model()`. `GET /tracking/options` — Returns `track.get_options()` plus `available_models` and `available_classes` for UI. `PATCH /tracking/options` — Body fields mapped to track setters; class names converted to IDs via config. `GET /tracking/warmup` — Legacy alias for load-model.
- **websocket.py:** `/ws` and `/ws-tracking` use `get_session_id_from_websocket(websocket)` and return the session’s camera track or tracking track from the factory (no query params; options are on the session instance).

### 8.6 Frontend

- **Tracking page:** Uses `loadModel: { url: "/tracking/load-model", readyText: "..." }` and `optionsUrl: "/tracking/options"`. On load: GET options → populate model, FPS, confidence, classes (multi-select), camera, mode → then GET load-model → enable Start. On option change: PATCH `/tracking/options`.
- **Raw stream page:** On load: GET cameras, then GET `/api/stream/options` (sets session cookie, can pre-fill camera/mode). On camera/mode change: PATCH `/api/stream/options`. WebSocket URL uses the same origin (no query params).
- **WebSocket URL:** Built as `ws://` + `location.host` + path (e.g. `/ws`, `/ws-tracking`). Path is normalized to a single leading slash. If the server sees a mangled path (e.g. `/ws//192.168.40.42%3A8000/ws`), the client is likely using a proxy or tunnel that rewrites the path; the fix is to open the app directly from the server’s URL (e.g. `http://<pi-ip>:8000/tracking`) in a normal browser.

## 9. Known Gotchas and Fixes

- **Session import:** In `stream_fastapi/session.py`, use `from .config import CAMERA_INDEX` (same package), not `..config`.
- **WebSocket 403 / wrong path:** If the server logs show a path like `/ws//192.168.40.42%3A8000/ws`, the request is being rewritten (e.g. by Cursor’s Simple Browser, a tunnel, or a reverse proxy). Have the user open the app at the server’s direct URL (e.g. `http://<pi>:8000/tracking`) in a normal browser so the WebSocket path stays `/ws` or `/ws-tracking`.
- **Default camera for tracking:** The session’s tracking track is created with `default_camera_index = CAMERA_INDEX` from `stream_fastapi/config.py` when `yolo/config/defaults.yaml` does not define `source.camera_index`. This can be switched to a yolo default later if desired.

## 10. File and Layout Reference

- **stream_fastapi/** — App, routes, session, config. Session stores per-session tracking and camera track instances.
- **stream_fastapi/session.py** — Session ID (cookie), get_tracking_track(sid), get_camera_track(sid).
- **pi/tracking_source.py** — `TrackingVideoTrack`: load_model(), setters, get_options(), _tracking_loop.
- **pi/picamera2_source.py** — `Picamera2Source` + module-level `list_cameras()`, `list_sensor_modes()`; class has setters and get_options().
- **yolo/** — config_loader, tracker (tracking_frames, run_tracking, get_target_class_ids), source_picamera, source_opencv, video_output, report. No model.py; callers use `YOLO(config.models[model_key]["weights"])`.
- **frontend/** — tracking.html, index.html, js/stream.js, css/main.css. stream.js uses config.wsPath, config.loadModel (or warmup), config.optionsUrl; builds WebSocket URL from location.host + path.
