Dependency Debugging Notes
==========================

Project: YOLO-Object-Tracking-Reporting-Model  
Host: Raspberry Pi 4B (aarch64, Cortex-A72)  
OS: Debian Trixie / Raspberry Pi OS (libcamera 0.7.0+rpt…)  

This document summarizes the dependency problems we hit, the wrong turns we took, and the final environment configuration we landed on. It’s meant as a historical record so you (or future you) can understand why the project is wired the way it is now.

----------------------------------------------------------------------
1. Initial Python 3.13 + pip Torch Attempt
----------------------------------------------------------------------

Starting point:
- System Python: 3.13.5 (`/usr/bin/python3 -> python3.13`).
- Objective: Run YOLO + Ultralytics with WebRTC tracking on this Pi OS.

What we tried first (pip wheels):
- Installed PyTorch / torchvision via pip for Python 3.13 from aarch64 wheel sources (kmtea and official manylinux wheels), e.g.:
  - `torch==2.10.0`, `torchvision==0.25.0` (`cp313` wheels, manylinux_2_28_aarch64).
- Result: **every import of `torch` on Python 3.13 crashed with `Illegal instruction` (exit code 132)**, even in tiny tests like:
  - `python -c "import torch; print(torch.__version__)"`.

Diagnosis:
- The `cp313` manylinux_2_28 aarch64 wheels are built assuming newer ARMv8.x features (e.g. LSE) than the Pi 4B’s Cortex-A72 actually has.
- As soon as you hit those instructions, the CPU issues `SIGILL` before Python can raise a normal exception.

Incorrect assumption:
- I initially took this as “Python 3.13 can’t run PyTorch on this Pi”, instead of “these particular pip wheels for cp313 are compiled for a newer ARM ISA.”

Consequence:
- We stopped pursuing Python 3.13 with pip-based torch, and pivoted to installing Python 3.12 from source and using that for ML.

----------------------------------------------------------------------
2. Python 3.12.12 from Source – ML Works, Camera Fails
----------------------------------------------------------------------

We built Python 3.12.12 from source under `/usr/src/Python-3.12.12` and installed it into `/usr/local`. Then:
- Created a 3.12 venv for the project.
- Installed:
  - `torch==2.3.1` (kmtea aarch64 wheel index).
  - `torchvision==0.18.1`.
  - `ultralytics==8.4.18`.

Results:
- `torch` and `torchvision` imported fine, **no illegal instruction** on 3.12.
- Ultralytics YOLO loaded and ran.
- FastAPI / uvicorn / aiortc code ran and served the app.

New blocker: camera stack (`picamera2` + libcamera bindings).
- `pip install picamera2` in the 3.12 venv succeeded, but:
  - `from picamera2 import Picamera2` → `ModuleNotFoundError: libcamera`.
- `yolo/pi_source.py` explicitly treats that as “picamera2 is not installed” and raises `RuntimeError("picamera2 is not installed")`.

We then tried to provide libcamera Python bindings for Python 3.12:

2.1. `rpi-libcamera` (PyPI)
---------------------------
- `pip install rpi-libcamera` in the 3.12 venv:
  - Fails at metadata generation with:
    - “This package works with libcamera version v0.5.0+…, but you have version v0.7.0+rpt20260205 installed.”
- Your OS ships **libcamera 0.7.0+rpt20260205-1**, not the 0.5.x series these bindings want.
- There is no 0.5.x libcamera package in your current apt repositories (`apt-cache policy` shows only 0.7.0+rpt, 0.6.0+rpt, and Debian’s 0.4.0).

2.2. `pylibcamera` (GitHub, Raspberry Pi official bindings)
-----------------------------------------------------------
- Cloned `https://github.com/raspberrypi/pylibcamera.git`.
- Installed build deps (meson, pybind11, etc.), then ran `pip install .` in the 3.12 venv.
- Result:
  - A strict version check in `meson.build` failed: wants libcamera `v0.5.2+99-bfd68f78`, but the system has `v0.7.0+rpt20260205`.
  - When we temporarily patched out that check, the C++ build still failed with missing headers:
    - `fatal error: libcamera/base/mutex.h: No such file or directory`
    - `fatal error: libcamera/base/log.h: No such file or directory`
  - This indicates a real API/layout mismatch between libcamera 0.5.x and 0.7.x, not just a version check guard.

2.3. System packages situation
------------------------------
- `apt-cache policy libcamera-dev libcamera-ipa libcamera0.*` shows:
  - `libcamera-dev 0.7.0+rpt20260205-1` (installed/candidate from Raspberry Pi repo).
  - `libcamera0.6 0.6.0+rpt20251202-1`.
  - `libcamera-dev 0.4.0-7` from Debian upstream.
- Crucially: **no libcamera 0.5.x** in your configured repos.

Conclusion on the 3.12 path:
- ML stack (`torch` + `torchvision` + Ultralytics) works great on 3.12.
- Camera stack is blocked because:
  - Both `rpi-libcamera` and `pylibcamera` target older libcamera versions (0.5.x).
  - Your OS has libcamera 0.7.0 and no 0.5.x packages.
  - The bindings don’t compile against 0.7.0, even when we brute-force the version check.

We also considered downgrading libcamera to 0.5.x on this OS, but:
- The required 0.5.x debs aren’t present in your current repositories.
- Manually hunting and pinning those versions would be brittle and invasive.

At this point, the 3.12 solution could only be made to work by **re-imaging** to an OS that ships the right libcamera version or by doing a heavy custom libcamera build, which is not a small dependency tweak anymore.

----------------------------------------------------------------------
3. Missed Option (Initially): Debian’s `python3-torch` for Python 3.13
----------------------------------------------------------------------

Important mistake:
- I kept assuming “torch is installed via pip inside the venv,” and treated apt-based `python3-torch` as a second-class option.
- This led me to prematurely rule out Python 3.13 entirely after seeing illegal instructions from pip wheels.

What we eventually tried:
- On the current OS, `apt-cache policy` shows:
  - `python3-torch 2.6.0+dfsg-7` for arm64.
  - `python3-torchvision 0.21.0-3`.
  - `python3-torchaudio 2.6.0-1`.
- Installing and testing under system Python 3.13:

  ```bash
  sudo apt install -y python3-torch python3-torchvision python3-torchaudio
  python3 -c "import torch, torchvision; print('system torch', torch.__version__, 'vision', torchvision.__version__)"
  ```

  Output:
  - `system torch 2.6.0+debian vision 0.21.0`

Critically:
- **No `Illegal instruction`** here.
- These Debian-packaged torch/vision builds are compiled for your actual CPU and are stable.

So:
- The original “PyTorch + Python 3.13 is impossible on this Pi” conclusion was wrong.
- The problem was **only with the pip manylinux cp313 wheels**, not with Debian’s python3-torch.

----------------------------------------------------------------------
4. Final Runtime Environment (Python 3.13 + venv with System Site-Packages)
----------------------------------------------------------------------

Given the above, we shifted to:

- **Python version**: System Python 3.13.5.
- **System packages (apt)** – recorded in `apt_requirements.txt`:

  ```bash
  sudo apt install -y \
    python3-torch python3-torchvision python3-torchaudio \
    python3-libcamera python3-picamera2 \
    libcamera-apps libcamera-dev \
    libcap-dev libgl1 libglib2.0-0 pkg-config
  ```

  These ensure:
  - Torch 2.6.0+debian, torchvision 0.21.0.
  - libcamera 0.7.0+rpt bindings for Python 3.13.
  - Picamera2 and camera apps matching the OS libcamera version.

- **Project venv**:

  ```bash
  cd ~/YOLO-Object-Tracking-Reporting-Model
  rm -rf venv
  python3 -m venv --system-site-packages venv
  source venv/bin/activate
  pip install -U pip
  pip install -r requirements.txt
  ```

  - The key is `--system-site-packages`: the venv can “see” the apt-installed torch/vision/libcamera/picamera2 without copying them.
  - We explicitly **uninstalled** any pip-installed `torch`/`torchvision` from the venv to avoid pulling in the bad cp313 wheels:

    ```bash
    pip uninstall -y torch torchvision
    ```

  - Then:

    ```bash
    source venv/bin/activate
    python -c "import torch, torchvision; print('venv torch', torch.__version__, 'vision', torchvision.__version__)"
    ```

    prints:
    - `venv torch 2.6.0+debian vision 0.21.0`

  - And Picamera2 is importable:

    ```bash
    python -c "from picamera2 import Picamera2; print('picamera2 OK')"
    ```

- **Project pip requirements (`requirements.txt`)**:

  ```txt
  ultralytics==8.4.18

  opencv-python-headless
  numpy
  PyYAML

  fastapi
  uvicorn[standard]

  aiortc
  av
  ```

  - Torch/torchvision are **not** listed here, because they come from apt as `python3-torch`/`python3-torchvision`.
  - `picamera2`/`libcamera` are also not in `requirements.txt` – they are supplied via apt and visible via `--system-site-packages`.

At this point:
- `python main.py` (with venv active) starts the server.
- `/` (raw stream) works: Picamera2 + WebRTC pipeline is good under Python 3.13.
- `/tracking` still has a **runtime rendering issue** (black output) in the tracking path, but that is now a **logic/pipeline problem**, not a dependency problem.

----------------------------------------------------------------------
5. Tracker Logic Changes vs. Black Screen
----------------------------------------------------------------------

While debugging the black-screen issue for `/tracking`, we made a few changes to the tracking code. Important distinction:
- These changes did **not** affect dependencies; they only changed how frames move through the YOLO pipeline.
- You explicitly wanted the parameter defaults for tracking functions to be tied to config values; that remains true.

Key files:
- `yolo/tracker_new.py`
- `pi/tracking_source.py`

5.1. Desired behavior (restored)
--------------------------------

You wanted:
- `tracking_frames` and `run_tracking` to:
  - Use defaults (model key, confidence, tracking flag, tracker file, and classes) pulled from `yolo/config/defaults.yaml` via `config_loader`.
  - Have those defaults visible directly in the function signatures, not via `None` and internal fallback.

Current signatures (after restoration):

```python
# yolo/tracker_new.py

config.load_config()
_DEFAULT_CLASS_NAMES: Optional[List[str]] = config.defaults.get("classes")
_DEFAULT_MODEL_KEY: str = config.defaults["model"]
_DEFAULT_CONF: float = float(config.defaults.get("conf", 0.5))
_DEFAULT_PERSIST: bool = bool(config.defaults.get("tracking", True))
_DEFAULT_TRACKER: str = "bytetrack.yaml"


def get_target_class_ids(
    class_names: Optional[List[str]] = _DEFAULT_CLASS_NAMES,
) -> Optional[List[int]]:
    ...


def tracking_frames(
    frame_stream: Generator[Any, None, None],
    model_key: str = _DEFAULT_MODEL_KEY,
    conf: float = _DEFAULT_CONF,
    persist: bool = _DEFAULT_PERSIST,
    tracker: str = _DEFAULT_TRACKER,
    classes: Optional[List[int]] = get_target_class_ids(),
    max_frames: Optional[int] = None,
    draw: bool = True,
) -> Generator[Tuple[Any, Any, Any], None, None]:
    ...


def run_tracking(
    frame_stream: Generator[Any, None, None],
    model_key: str = _DEFAULT_MODEL_KEY,
    conf: float = _DEFAULT_CONF,
    persist: bool = _DEFAULT_PERSIST,
    tracker: str = _DEFAULT_TRACKER,
    classes: Optional[List[int]] = get_target_class_ids(),
    ...
) -> Dict[str, Any]:
    ...
```

This matches your design preference: callers that don’t provide overrides get the exact values from `defaults.yaml` via the function signature.

5.2. What caused black screen vs. what we tried
-----------------------------------------------

Symptom:
- `/tracking` WebRTC connection opens without error; libcamera configures the sensor; Ultralytics initializes (and auto-installs `lap>=0.5.12`).
- But the video element on the `/tracking` page shows a black image.
- Raw `/` path continues to show live camera frames.

Key observation:
- When we **bypassed YOLO** in `TrackingVideoTrack` and just streamed raw frames from `picamera2_frame_stream`, `/tracking` started showing normal video.
- This proves:
  - WebRTC + aiortc wiring for `/ws-tracking` is correct.
  - The camera frames from Picamera2 are fine.
  - The black screen is localized to the **tracking pipeline** (YOLO + drawing + frame handoff).

We experimented with:
- Making copies of frames (`model_input`, `display_frame`) so `model.track` and `video_output.draw_detections` couldn’t corrupt the same buffer.
- Passing different kwargs through `tracking_frames` from `TrackingVideoTrack`.

These experiments didn’t fix the black screen and, at one point, unintentionally removed the config-based defaults you wanted. Those defaults have since been restored.

Current status:
- Dependencies are correctly set up (Python 3.13 with distro torch, libcamera, picamera2).
- `/` and the Picamera2 WebRTC path are stable.
- `/tracking` black-output issue is now purely a **pipeline logic bug** in the tracking path, not a version or dependency issue.

----------------------------------------------------------------------
6. Summary: Lessons and Final Patch
----------------------------------------------------------------------

Main takeaways:

1. **Don’t assume pip is the only way to get torch** on a Pi.
   - For Python 3.13, pip wheels for cp313 were broken for your CPU, but Debian’s `python3-torch` was fine.
   - The correct play was to try distro `python3-torch` much earlier.

2. **Python 3.12 from source**:
   - Was a valid way to get good PyTorch wheels, but ran into a wall with libcamera 0.7.0 because all official bindings we tried target 0.5.x.
   - Without an OS that ships the matching libcamera version, 3.12 couldn’t easily host the full camera+tracking stack.

3. **Current recommended runtime**:
   - Python 3.13 system interpreter.
   - Project venv created with `--system-site-packages` to see distro torch, libcamera, picamera2.
   - Torch/vision/libcamera/picamera2 via apt (`python3-torch`, `python3-torchvision`, `python3-libcamera`, `python3-picamera2`).
   - Other Python deps (`ultralytics`, `fastapi`, `aiortc`, `opencv-python-headless`, etc.) via pip in the venv.

4. **Tracker defaults**:
   - `tracking_frames` and `run_tracking` now default their parameters to values taken directly from `yolo/config/defaults.yaml` via `config_loader` (as intended).
   - Their signatures are stable and no longer part of the “black-screen” experimentation.

5. **Outstanding work**:
   - `/tracking` still renders black even though the dependencies are correct and `/` works.
   - Debugging that now means instrumenting the tracking loop itself (e.g., confirming that `tracking_frames` yields frames regularly and that the BGR→RGB conversion upstream isn’t accidentally feeding zeros), not changing Python or libraries.

This file is the “source of truth” for how and why the current environment is set up the way it is, and which past approaches we abandoned (3.12 libcamera bindings, pip torch for cp313, etc.). It should help you evaluate any future OS or Python changes with full knowledge of the trade-offs we discovered here.
